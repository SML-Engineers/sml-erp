# Backlog — Phase 0 + Phase 1 (core foundation and payment vouchers)

Work top to bottom. Each task is one pull request. A task is done when every acceptance
criterion is covered by a passing test (or, for pure UI items, checked on the test server by
the owner). Spec references point to `docs/spec.md`.

Status: `[ ]` to do · `[x]` done

---

## A. Project foundation

- [x] **P0-01 Project skeleton**
  Docker Compose with Django, PostgreSQL, Redis, S3-compatible file storage, Celery worker, React (Vite) dev
  server and Nginx. `make up`, `make test`, `make migrate` commands. `.env.example`.
  - `make up` starts everything; the API health endpoint returns 200; the React app loads.
  - `make test` runs backend and frontend tests (one sample test each) and passes.
  - No secrets committed.

- [x] **P0-02 Continuous integration and locked dependencies**
  GitHub Actions workflow running lint and all tests on every pull request (added in P0-01).
  Exact dependency locks with hashes, generated by a workflow; CI and Docker install only from
  them; Dependabot update proposals (docs/decisions/0001). Protection of `main`
  (docs/decisions/0003).
  - [x] A failing test makes the pull request check fail.
  - [x] CI and Docker images install exact locked versions only; CI fails if a lock is missing.
  - [x] `main` changes only through pull requests with passing checks: by agreed practice for
    now (owner's decision, docs/decisions/0003); enforced by GitHub when revisited at go-live.

- [x] **P0-03 Login and user accounts**
  Email + password login (Argon2 hashing), logout, session timeout, password change,
  login history. Two-factor authentication (TOTP) for users with Accountant, Director,
  Cashier or Admin roles.
  - Users with those roles cannot reach any page until 2FA is set up.
  - Failed logins are recorded; 5 failures in 15 minutes locks the account for 15 minutes.

- [x] **P0-04 Roles, permissions and data scope** (spec 1.1, 1.2)
  Permission model: areas × access levels (none, View, Enter, Approve, Manage) plus special
  actions (record payments, delete submitted voucher, close period, change bank details,
  export personal data, manage users and roles). Standard roles loaded with the default access
  matrices in spec 1.2 (Phase 1 roles active: System Administrator, Director, Accountant,
  Accounts Clerk, Cashier, Auditor). Admin can create custom roles by ticking permissions.
  Holding the Accountant, Director, Cashier or System Administrator role sets the user's
  `two_factor_required` flag automatically (built in P0-03).
  A user can hold several roles. Data scope per user: divisions, and sections for production
  staff. Deny by default: menus show only permitted areas, and every API endpoint checks the
  effective permission and data scope on the server.
  - An endpoint called without the required permission returns 403. (Hiding the area from the
    menu is part of P0-06; the user's access is already sent to the app in /auth/me/.)
  - Section scope for production staff is added with sections in P0-09.
  - The division records WS, IM and HO are created here so scope works; their control panel
    is P0-07.
  - A user scoped to one division cannot see or change another division's records, through
    lists, reports, exports or direct API calls.
  - Auditor can read everything and change nothing.
  - The System Administrator has no access to payments, banking, accounting or financial
    reports by default.
  - Assigning a conflicting combination (Clerk + Cashier, Accountant + Cashier, Admin + any
    finance role) shows a warning and records the reason in the audit log.

- [x] **P0-04b User access overrides and access administration** (spec 1.3)
  User access page: roles, data scope, and a grid of every area and action showing role
  default, override and effective access. Admin can grant or remove access per user with a
  mandatory reason and optional end date; copy access from another user; reset to role
  defaults; full history. Joiner / mover / leaver actions. Quarterly access review report.
  - A removal override beats any grant, from a role or another override.
  - An override that grants a sensitive permission (approve vouchers at any level, record
    payments, delete vouchers, change bank details, close periods, manage users and roles,
    payroll) has no effect until the Director confirms it. Removals take effect immediately.
  - An expired temporary override stops working on its end date, and the user is notified.
  - No override can let a user approve their own document, approve at two levels, or skip the
    Director on a voucher (tested directly against the hard controls).
  - The Admin cannot change their own roles or overrides.
  - Deactivating a leaver ends all their sessions at once and removes their overrides; their
    records and history remain.
  - Accounts unused for 90 days (configurable) are deactivated automatically.
  - Every grant, removal, confirmation and expiry is recorded: each override keeps who
    created, confirmed and ended it, when and why, and is never deleted. P0-05 adds these
    events to the general audit log as well.

- [x] **P0-05 Audit log** (spec 3)
  Insert-only log of create/update/delete on audited models: user, time, IP, old and new values.
  Includes every access change: users, roles, divisions, overrides, confirmations, expiries,
  deactivations and access reviews.
  - Updating or deleting an audit row fails at database level.
  - A change writes one audit row with old and new values (tested on divisions and users;
    the supplier bank-account case is tested with suppliers in P0-13).
  - Passwords and other secrets never appear in the log; routine fields such as the last
    sign-in time are not logged.
  - Every row records who (or "system" for scheduled jobs), when, the address, the event and
    the reason. Auditor, Director and Admin can read and filter it; nobody can change it.

- [x] **P0-06 Application layout**
  Sidebar navigation, top bar with notification bell and user menu, responsive layout
  (works on a phone), shared table component with search, sort, paging and column totals.
  - The menu shows only the areas the user can view (from their access in /auth/me/).
  - Table: page sizes 10 / 25 / 50 / All, "Showing X to Y of Z entries", search, sortable
    columns, and money totals added exactly (no floating-point rounding).
  - The notification bell is in place; its count arrives with notifications in P0-18.

## B. Master data and admin settings

- [x] **P0-07 Company and divisions** (spec 3, 3.1)
  Company profile (name, registration, VAT no., base currency LKR, financial year start).
  Division master maintained by the Admin: two-character code (PP), name, type (Production or
  Shared), default bank account (added in P0-14, once bank accounts exist), active. Seed:
  WS Workshop, IM Plastic Injection Moulding, HO Head Office (shared costs), as confirmed by
  the owner. Divisions are added, renamed and
  deactivated by the Admin from the Divisions control panel.
  - A division's code cannot change once it has been used on any document.
  - A division with transactions cannot be deleted, only deactivated.
  - A division added through the control panel on a running system is usable immediately:
    no restart, deployment or code change (test: create through the API, then use it at once).
  - A new division appears in every division picker, filter and report, gets its own voucher
    numbering, and leaves existing divisions' records and figures unchanged.

- [x] **P0-08 Number series** (spec 3)
  Number formats built from tokens, set by the Admin per document type: code (PP), year
  (YY / YYYY), month (MM), day (DD), running number (XXX / NNNN) with a reset period
  (daily, monthly, yearly or never). Allocated inside the saving transaction. Tokens are
  written in braces so they cannot be confused with fixed text: {PP}{YY}{MM}{DD}{XXX},
  PI-{YYYY}-{NNNN}.
  - Voucher format PPYYMMDDXXX, PP = the voucher's division code: the third IM voucher on
    2026-10-23 is IM261023003.
  - The running number restarts at 001 each day, separately for each division.
  - 50 concurrent saves produce 50 unique, consecutive numbers.
  - A number is never reused, including after its document is deleted.
  - Creating a 1,000th document with a 3-digit running number on one day is refused with a
    clear message (the Admin can widen the running number).

- [x] **P0-09 Divisions, sections and machines page** (spec 3A.1)
  Tree view Division → Section → Machine with add/edit forms, Excel import and export
  (divisions themselves come from P0-07).
  Moulding machine extra fields. Seed: Workshop division with the 18 sections from spec 3A.1,
  Moulding division. No machines are seeded: the Admin adds all of them from this page.
  - A section or machine used on a transaction cannot be deleted, only deactivated.
  - Codes cannot change once used.
  - Section scope for production staff (from P0-04): a user can be limited to particular
    sections, and sees the sections they supervise. "Copy access from another user" does not
    copy sections yet; it is added with the production pages (Phase 3).

- [x] **P0-08b Tax invoice and quotation numbers** (spec 3, 6.1; owner's sample invoice)
  Number series gains {MMM} (month letters, e.g. SEP), {IC} (the division's tax invoice code,
  set by the Admin on the Divisions page) and a choice of what happens when a running number is
  full: stop, or carry on with more digits. Starting series: tax invoices {YY}{MMM}_{IC}_{XX}
  (monthly, per division), quotations QL{YY}{MM}{DD}{XX} (daily), proformas PI-{YYYY}-{NNNN}.
  - The 35th W1 invoice of September 2026 is 26SEP_W1_35; the serial restarts at 01 each
    month for each division, and the 100th is 26SEP_W1_100.
  - The 5th quotation of 21 October 2026 is QL26102105.
  - A division's tax invoice code is 1 to 15 letters or digits, unique, and fixed once used
    on an invoice (application and database); an invoice for a division without one is refused.

- [x] **P0-10 Shifts and rosters page** (spec 3A.2)
  Tabs: Shifts, Roster patterns, Crews, Roster calendar with 4-week preview and the warnings
  listed in the spec. Seed: General shift 08:00–17:00.
  - A night shift is attributed to the date it started.
  - Rosters are dated: one cannot start in the past, and once started only its end date can
    change; shift times and pattern days used by a started roster are fixed.
  - A crew can follow only one roster at a time (refused, not just warned).
  - Crew members are picked from the employee register, added with the HR module.

- [x] **P0-11 Currencies and exchange rates page** (spec 3A.4)
  Pre-loaded currencies (USD, EUR, GBP, AUD, JPY, CNY, INR, SGD, AED); daily rate entry and CSV import.
  - When no rate exists for a date, the latest earlier rate is returned and flagged.
  - The Admin keeps the currency list; the Accountant enters rates (Accounting: Enter).
  - A rate used on a document never changes (application and database); LKR is fixed.

- [x] **P0-12 Quotation approval limits page** (spec 3A.3)
  Minimum margin % and value limit per division, effective-dated. A change entered by the
  Admin takes effect only after Director confirmation.
  (Used in Phase 1.5; built now because it is an admin setting.)
  - The Director cannot confirm a change they entered (rule 5); one pending change per
    division; confirmed limits are never changed or deleted (database).
  - Without confirmed limits, every quotation of that division goes to the Director.
  - Per customer group limits wait for customer groups (Phase 1.5).

- [x] **P0-13 Suppliers and payees** (spec 4.1)
  Supplier master: code, name, payee category (Supplier, Utility, Bank or credit card,
  Government, Employee, Other), address, contacts, VAT no., bank details, payment terms,
  currency, active. Bank detail changes are audited and shown to the Accountant on the next voucher.
  - Duplicate VAT number warns before saving.
  - Changing a supplier's bank account writes one audit row with the old and new value
    (register the supplier model with the audit log, P0-05).
  - Codes come from the number series (S0001…). Clerks add payees and edit contact details;
    the Accountant deactivates; bank details need the "change bank details" action. A bank
    change stays flagged until the Accountant acknowledges it (on the voucher in P1-03).

- [x] **P0-14 Bank and cash accounts**
  Company bank accounts and cash/petty cash accounts linked to ledger accounts; cheque books
  with number ranges. Adds each division's default bank account (moved here from P0-07).
  - The default is chosen by the Accountant on the Bank and cash accounts page, not on the
    Divisions page: the Admin has no banking access by default.
  - Each cheque number is used once, ever (issued or spoiled with a reason; database).
  - The link to ledger accounts is added with the chart of accounts (P0-15, done).

## C. Accounting core

- [x] **P0-15 Chart of accounts, QuickBooks style** (spec 3)
  Accountant adds, edits, merges and deactivates accounts from the Chart of Accounts page.
  QuickBooks account types and editable detail types, sub-accounts to any depth, optional
  account numbers, default tax code and division, system accounts that cannot be removed,
  Excel import and export. Starter chart for a manufacturing company loaded at setup.
  - An account with transactions cannot be deleted, only made inactive.
  - Merging two accounts moves all history to the remaining account; totals are unchanged.
  - An account's type cannot be changed once it has transactions in a closed period.
  - A sub-account must have the same report section as its parent (e.g. no expense
    sub-account under a bank account).
  - Done as in QuickBooks: a sub-account has the same account type as its parent (each
    type is its own block on the reports), which also keeps it in the same report section.
  - A merge never rewrites posted entries (rule 3): the merged account keeps them, becomes
    inactive and points at the remaining account, and reports count its history there
    (`roll_up`). Its sub-accounts and bank link move. A merge cannot be undone (database).
  - A used account's number is fixed once it has one (rule 9); names can always change.
  - Company bank and cash accounts are linked to a Bank-type ledger account (finishes P0-14);
    the link is fixed once the account is used. Payments (P1-07) will require it.
  - Moved to P0-16, where periods are built: the closed-period type check.
  - Deferred to the tax codes task: the default tax code per account (tax design waiting
    for the owner's QuickBooks tax list). The default division is done.

- [x] **P0-16 Journal and periods** (spec 3)
  `journal_entry` / `journal_line`, posting service, reversal service, accounting periods
  with close/reopen (Director only).
  - An unbalanced entry is refused (service and database).
  - Updating or deleting a posted entry fails at database level.
  - Posting into a closed period is refused.
  - Reversal creates a mirror entry linked to the original.
  - A line on an income or expense account without a division is refused (spec 3.1).
  - Profit and loss by division for a date range equals the company total when summed.
  - An account's type cannot be changed once it has entries in a closed period (from P0-15).
  - Posting marks the account used (`accounting.services.mark_used`) and refuses inactive or
    merged accounts; reports count a merged account's entries under the remaining account.
  - Only posted entries are stored (drafts live on their source documents), so there is no
    status column. Numbers come from a new "journal" series, JV{YY}{MM}{NNNN}, monthly.
  - Balance is checked by the service and by a deferred database trigger when the saving
    transaction commits (an entry and its lines are saved together). Posting also refuses
    inactive or merged accounts and income or expense lines without a division (database too).
  - Lines carry a supplier as the party; customers are added with them in Phase 1.5.
  - Months are calendar months; only a month that has ended can be closed; reopening needs a
    reason. Manual journal entry (with approval) stays in Phase 2: posting is called by the
    voucher and payment services; the Accountant can reverse an entry on the Journal page.

- [x] **P0-17 Approval engine** (spec 3)
  Generic engine: approval matrix per document type (levels, roles, conditions), approval log
  (insert-only), actions Submit / Approve / Return / Reject, segregation of duties.
  - Creator cannot approve their own document.
  - The same user cannot approve at two levels.
  - Return and Reject without a reason are refused.
  - Built in `apps.core.approvals`. Level 1 is the submitter; approval levels start at 2.
    The route is copied onto the document when it is submitted, so a matrix change never
    alters a document already on its way (rule 11); a returned document gets a fresh route.
  - Segregation (rule 5) and the reason for Return and Reject are also enforced by the
    database. Only the creator submits. An approver must hold the level's role and work in
    the document's division.
  - The Admin keeps the matrix on Settings → Approval matrix: rules are added or switched
    off, never edited. For vouchers the matrix always keeps at least two approval levels that
    apply to every voucher, the last being the Director (rule 6).
  - The approval queue page and the voucher's own statuses come with the vouchers (P1-04).

- [x] **P0-18 Notifications**
  In-app bell and email for: voucher awaiting my approval, voucher returned to me,
  voucher approved/rejected. Per-user on/off settings.
  - Raised by the approval engine for every document type, so vouchers (P1-04) get them
    without further work: waiting for my approval (everyone who can act at the level, never
    the creator), returned to me (with the reason), approved, rejected (with the reason).
  - Notifications are written in the same transaction as the action; emails go out through
    the background worker after it commits, with a five-minute job sending any still waiting.
    Each email is sent once. Read notifications are tidied after 180 days.
  - My notifications page (user menu): bell and email on or off per kind of event.
  - The reminder for vouchers waiting too long (spec 4.3, optional) is left for later.
  - Servers need an SMTP account (EMAIL_* settings) and APP_URL for links in emails.

- [ ] **P0-19 Sending documents and reports by email** (spec 3B; owner, 29 Oct 2026)
  Settings → Document email: the sending mailbox (e.g. finance@domain.com) with its mail
  server, password stored encrypted, a test email; default subject and body per kind of
  document or report, with placeholders. A send form whose message can be edited before
  sending; an insert-only record of every email sent. Each document and report module adds
  its Email button using this (quotations, invoices, statements, outstanding reports…).
  - The password is never returned by the API, and only the Admin changes the settings.
  - A template with an unknown placeholder is refused.
  - The edited subject and body are what is sent and what is recorded.
  - Sending without a configured account, to an invalid address, or to more than 20
    recipients is refused; a failed send is recorded with the error.
  - The sent-email record cannot be changed or deleted (database).

## D. Payment vouchers (Phase 1)

- [ ] **P1-01 Voucher types** (spec 4.1)
  Seed: Cheque Payment, Online Payment, Petty Cash, Internal Transfer, Supplier Advance,
  Staff Reimbursement. Admin can add types. The type is a field and a list filter; it is not
  part of the voucher number.

- [ ] **P1-02 Voucher entry — Clerk** (spec 4.4, 4.5)
  Create voucher with division, type, supplier (with outstanding balance), lines, multiple scanned
  attachments (PDF/JPG/PNG, drag-and-drop and phone camera), save draft, submit.
  The number (PPYYMMDDXXX, P0-08) is given on first save, using the voucher's division code.
  - Same supplier + invoice number already on another voucher shows a warning.
  - An uploaded file identical (SHA-256) to an existing attachment shows a warning.
  - Files larger than 20 MB or of other types are refused.

- [ ] **P1-03 Accountant review** (spec 4.4)
  Queue of submitted vouchers; invoice preview beside details; set GL account, division,
  tax per line (and optional job/production order field, unused until Phase 3);
  approve / return / reject.
  - A voucher cannot be approved at L2 while any line lacks an account or division.
  - A line can be split across divisions by amount or %; the split must add up to the line total.

- [ ] **P1-04 Director approval page** (spec 4.4; replaces the current page)
  Type tabs with pending counts; table with Approve and Reject columns, reason box, bulk
  Approve all / Reject all / Clear all, Confirm and Reset; side panel with invoice preview,
  lines, Accountant's comment, supplier balance and aging; filters and totals; phone layout.
  - Confirm with any Reject lacking a reason is refused and the row is highlighted.
  - Bulk approval shows the count and total amount before confirming.

- [ ] **P1-04b Row actions: Resources, Print, Edit, Delete** (spec 4.4, as in the current system)
  Actions menu (⋯) on every voucher row, plus a paperclip icon when attachments exist.
  Resources opens an attachment viewer (page, zoom, rotate, download). Print produces the
  company-format payment voucher PDF (A4 default, A5 option) with prepared / checked /
  approved names, dates and times from the approval log, and the total in words.
  - Actions a user may not take are hidden AND refused by the API.
  - Edit: Clerk only on Draft/Returned; Accountant only at L2; Director only at L3. A Director
    change to payee, amount or lines returns the voucher to the Accountant with the change shown.
  - After Director approval, Edit is replaced by Amend.
  - Delete: a never-submitted Draft by its creator or the Admin; a submitted voucher with no
    payment by the Director or the Admin only, with a mandatory reason.
  - A deleted voucher is a soft delete: status Deleted, hidden from working lists, listed with
    its full history in a Deleted Vouchers report, number never reused.
  - Deleting a voucher with any payment is refused at service and database level.
  - Reprints are watermarked "Copy"; every edit, delete and print is in the audit log.

- [ ] **P1-05 Returns and amendments** (spec 4.2)
  Returned vouchers go back to the Clerk; resubmission restarts at L2. Amending an approved,
  unpaid voucher creates a new revision that goes through L2 and L3 again; Amendments List.
  - An approved voucher cannot be edited directly.

- [ ] **P1-06 Cancellation** (spec 4.2)
  Accountant requests cancellation of an unpaid voucher; Director approves.
  - A voucher with any payment cannot be cancelled.

- [ ] **P1-07 Supplier payments and the payment lock** (spec 4.6)
  Cashier screen listing Director-approved unpaid vouchers; payment created from a voucher
  only; bank account, method, cheque/transfer reference, date; partial payments; posts the
  journal entry; prints the payment voucher. PostgreSQL trigger as in the spec.
  - Payment for a voucher in any status other than Director Approved / Partly Paid is refused
    by the service AND by the database trigger (test both, including a raw SQL insert).
  - Total payments can never exceed the approved amount (including concurrent payments).
  - Fully paid voucher becomes Paid and locked.
  - Each payment produces a balanced journal entry (Dr supplier payable/expense, Cr bank).
  - Cheque numbers cannot be reused within a cheque book.

- [ ] **P1-08 Lists and reports** (spec 4.4)
  Voucher List, Approved List, Amendments List; vouchers pending by approver and age;
  payments by period; approval history of any voucher; export to Excel and PDF.

- [ ] **P1-09 Reminders**
  Daily reminder to approvers for vouchers waiting longer than a configurable number of days.
